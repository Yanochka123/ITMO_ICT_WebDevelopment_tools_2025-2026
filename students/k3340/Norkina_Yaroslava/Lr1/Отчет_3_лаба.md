# Лабораторная работа №3: Упаковка FastAPI приложения в Docker, Работа с источниками данных и Очереди


Была создана БД для программы тайм-менеджера, согласно описанию в варианте. На основе предоставленных данных о функционале был создан код для запуска проекта тайм-менеджмента через файл main.py с временной БД и API эндпоинтами, аналогично практике 1.

Цель: научиться упаковывать FastAPI приложение в Docker, интегрировать парсер данных с базой данных и вызывать парсер через API и очередь.

Сервисы Docker Compose
В docker-compose.yml описаны следующие сервисы:

Сервис	Назначение	Порт
app	основное FastAPI-приложение	8000:8000
parser_service	отдельный сервис парсера	8001:8001
db	PostgreSQL	5433:5432
redis	очередь задач	6380:6379
celery_worker	обработчик фоновых задач	без внешнего порта
Снаружи PostgreSQL доступен на порту 5433, чтобы не конфликтовать с локальным PostgreSQL или контейнером из первой лабораторной работы.

Подзадача 1. Упаковка в Docker
Были созданы Dockerfile для:

основного FastAPI-приложения;
сервиса парсера;
Celery worker.
Также был создан общий docker-compose.yml, который запускает все необходимые сервисы одной командой:

docker compose up --build
При запуске основного приложения автоматически выполняются миграции Alembic.

Подзадача 2. Вызов парсера из FastAPI по HTTP
В основное FastAPI-приложение был добавлен эндпоинт:

POST /parser/parse
Он принимает URL, отправляет HTTP-запрос в контейнер parser_service, получает результат парсинга и возвращает его пользователю.

Пример запроса:

{
  "url": "https://example.com/"
}
Пример ответа:

{
  "url": "https://example.com/",
  "title": "Example Domain",
  "saved_id": 1,
  "saved_to": "tag"
}
Подзадача 3. Вызов парсера через очередь
Для выполнения парсинга в фоне были добавлены Redis и Celery.

Основное приложение добавляет задачу в очередь через эндпоинт:

POST /parser/parse-async
Пример ответа:

{
  "message": "Parsing task started",
  "task_id": "...",
  "status_url": "/parser/tasks/..."
}
Celery worker забирает задачу из Redis, выполняет парсинг и сохраняет результат в общую PostgreSQL-базу.

Для проверки статуса задачи добавлен эндпоинт:

GET /parser/tasks/{task_id}
Пример успешного результата:

{
  "task_id": "...",
  "status": "SUCCESS",
  "result": {
    "url": "https://example.com/",
    "title": "Example Domain",
    "saved_id": 2,
    "saved_to": "tag"
  }
}
Проверка работы
После запуска проекта доступны:

http://127.0.0.1:8000/docs  — основное FastAPI-приложение
http://127.0.0.1:8001/docs  — сервис парсера
Проверка прямого вызова:

Открыть http://127.0.0.1:8000/docs.
Выполнить POST /parser/parse.
Указать URL https://example.com/.
Проверить, что вернулся заголовок страницы и saved_id.
Проверка очереди:

Выполнить POST /parser/parse-async.
Скопировать task_id.
Выполнить GET /parser/tasks/{task_id}.
Проверить, что задача перешла в состояние SUCCESS.
Вывод
В третьей лабораторной работе FastAPI-приложение, база данных, парсер, Redis и Celery worker были упакованы в Docker Compose. Основное приложение может вызывать парсер напрямую по HTTP или ставить задачу парсинга в очередь. Все сервисы используют одну общую PostgreSQL-базу данных, что соответствует замечанию о недопустимости создания отдельной базы для каждого микросервиса.
